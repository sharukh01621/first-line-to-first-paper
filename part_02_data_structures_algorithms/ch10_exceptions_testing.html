Learning Objectives

By the end of this chapter, you will be able to:

  1. Trace and apply every clause of Python’s try / except / else / finally exception-handling lifecycle.
  2. Catch specific exception classes (ValueError, TypeError, KeyError) using EAFP style while avoiding the silent-bug trap of bare except:.
  3. Enforce defensive clinical and statistical input contracts by choosing deliberately between returning None (valid but undefined) and raising ValueError (impossible or corrupt input).
  4. Define domain-specific custom exceptions (such as InvalidVitalSignError(ValueError)) to make research error logs immediately readable to collaborators and reviewers.
  5. Write automated assert and pytest-style unit tests—including boundary checks, floating-point tolerances, and expected-exception checks—to catch broken formulas before submission.
  6. Apply a repeatable four-step Systematic Debugging Protocol (Reproduce \(\rightarrow\) Isolate \(\rightarrow\) Inspect \(\rightarrow\) Lock In with a Regression Test) to eliminate bugs permanently.

10.1 Stage 1 — First-Principles Intuition: Loud Failures Beat Silent Retractions

When a novice’s script crashes with a red traceback, their first instinct is frustration. Yet in scientific computing, a loud crash is a gift. The true nightmare of computational research is a program that never crashes, silently converts a stray "999" sentinel or missing hemoglobin value into a distorted cohort mean, and prints a clean-looking Table 1 that triggers a journal retraction two years later.

Defensive programming and automated testing invert that risk: you teach your code to inspect every incoming value at the gate, reject impossible inputs loudly, quarantine corrupt rows cleanly during batch runs, and verify every mathematical formula automatically before a single number enters your manuscript.

NoteMental Model — The Biosafety Specimen Intake Airlock

Think of every research function as a biosafety laboratory with a double-door intake airlock:

  1. Gate Inspection (raise ValueError): Before running any assay, the intake technician checks the specimen label, sample type, and physical plausibility (e.g., human body temperature between \(30.0\) and \(45.0\) degrees Celsius). Impossible samples are rejected loudly so they can never contaminate the downstream database.
  2. Quarantine Tray (try / except): When processing a crate of \(5{,}000\) field tubes, one cracked vial should not shut down the entire hospital lab. A batch controller wraps each tube inside try / except ValueError, routing clean samples to the analysis rack and logging rejected tubes into a written quarantine ledger.
  3. Guaranteed Sterilization (finally): Whether a test succeeds or fails, the technician always logs the timestamp and closes the file handle or freezer door.
  4. Daily Calibration Controls (assert / Unit Tests): Every morning, the lab runs known control standards (e.g., \(70\text{ kg}\) at \(1.75\text{ m}\) must yield BMI \(\approx 22.86\)) before trusting real patient results. If a calibration test fails, an AssertionError halts the bench immediately.

10.1.1 Two Idioms: LBYL vs. EAFP

Python programmers recognize two complementary styles of defensive coding:

  • LBYL (Look Before You Leap): Explicitly check preconditions (if key in d:, if cases == 0:) before acting. Ideal for validating clinical bounds and None guards.
  • EAFP (Easier to Ask for Forgiveness than Permission): Attempt the operation directly inside try: and handle the exact failure (except (KeyError, TypeError):). Ideal for parsing dirty strings (float(raw_val)) and reading deeply nested JSON/dictionary payloads.

10.2 Stage 2 — Visual Mental Model: Exception Control-Flow & Systematic Debugging

Every try statement follows one exact deterministic path through its four clauses (try, except, else, finally). Study the routing diagram carefully:

Notice two subtleties that even experienced researchers sometimes miss:

  • else: runs only when try: raises zero exceptions. Keeping post-parse logic inside else: keeps the try: block tiny so you never accidentally swallow a bug from later lines!
  • finally: always runs—even if try: succeeded, even if except: caught an error, even if an uncaught exception is about to crash the script, and even if try: executes a return statement.
TipThe 4-Step Systematic Debugging Protocol

Never “guess and randomly edit lines” when a script misbehaves. Follow the same scientific method you use at the lab bench:

  1. Reproduce: Shrink the failure to the smallest input that triggers the bug reliably (e.g., a single patient dictionary instead of a CSV of \(10{,}000\) rows).
  2. Isolate: Read the traceback bottom-up—last line gives the exception class and message; the line immediately above shows the exact failing expression. Narrow down which function first produces a wrong value.
  3. Inspect: Print intermediate values and types (print(repr(x), type(x))) or trace one call frame by hand. Verify assumptions (e.g., is "38.5" a str, or is True sneaking past isinstance(x, int)?).
  4. Verify & Lock In: Once fixed, add an assert test for that exact failing input so the bug can never return silently in a future revision.

10.3.1 Full Exception Lifecycle: try / except / else / finally

def parse_reading_with_audit(raw_text):
    """Demonstrate full try / except / else / finally lifecycle."""
    try:
        value = float(raw_text)
    except (ValueError, TypeError) as exc:
        print(f"  [EXCEPT] Rejected {raw_text!r}: {exc}")
        result = None
    else:
        print(f"  [ELSE]   Parsed clean float: {value}")
        result = value
    finally:
        print("  [FINALLY] Audit entry closed.")
    return result

r1 = parse_reading_with_audit("38.4")
r2 = parse_reading_with_audit("N/A")
print("Returned:", r1, r2)

Expected Output:

  [ELSE]   Parsed clean float: 38.4
  [FINALLY] Audit entry closed.
  [EXCEPT] Rejected 'N/A': could not convert string to float: 'N/A'
  [FINALLY] Audit entry closed.
Returned: 38.4 None

Look closely at the execution order:

  • For "38.4", float("38.4") succeeds, so Python skips except, enters else, and closes with finally.
  • For "N/A", float("N/A") raises ValueError, so Python jumps directly into except (ValueError, TypeError) as exc:, skips else, and still runs finally.
  • Binding the exception object with as exc gives you the exact diagnostic message for your audit log.

10.3.2 Specific Exceptions & EAFP Nested Dictionary Lookups

Surveillance APIs and clinic JSON exports frequently omit districts, drop optional metrics, or store None for an entire division that failed to report. With EAFP, a single compact try / except (KeyError, TypeError) safely guards every failure mode at once:

surveillance = {
    "Dhaka": {"cases": 140, "deaths": 3},
    "Sylhet": {"cases": 25, "deaths": 0},
    "Barishal": None,
}

def get_metric(report, district, metric):
    """Fetch nested metric safely via EAFP."""
    try:
        return report[district][metric]
    except (KeyError, TypeError):
        return None

print("Dhaka cases:   ", get_metric(surveillance, "Dhaka", "cases"))
print("Sylhet deaths: ", get_metric(surveillance, "Sylhet", "deaths"))
print("Barishal cases:", get_metric(surveillance, "Barishal", "cases"))
print("Missing dist:  ", get_metric(surveillance, "Khulna", "cases"))

Expected Output:

Dhaka cases:    140
Sylhet deaths:  0
Barishal cases: None
Missing dist:   None
WarningNever Write a Bare except: in Research Code!

Writing a naked except: (without naming specific exception classes) catches everything—including NameError from a misspelled variable, ZeroDivisionError from a math bug, and even KeyboardInterrupt when you try to stop a runaway loop! Always name the narrowest tuple of expected exceptions, such as except (ValueError, TypeError): or except (KeyError, TypeError):.

10.3.3 Defensive Programming: raise ValueError vs. Returning None

A common design question in biostatistics is: “When an input looks wrong, should my function return None or raise ValueError?” Follow this crisp scientific rule:

  • Return None when the input is factually valid, but the statistic is mathematically undefined (for example, cases == 0 in a quiet week where Case Fatality Rate \(0 / 0\) is undefined).
  • raise ValueError when the input is physically or logically impossible (for example, negative deaths or negative cases—a sure sign of corrupted data).
def compute_cfr(deaths, cases):
    """Compute Case Fatality Rate (%), raising on impossible counts."""
    if deaths < 0 or cases < 0:
        raise ValueError("deaths and cases must be non-negative")
    if cases == 0:
        return None
    return round((deaths / cases) * 100, 2)

print("Valid CFR (12/400):", compute_cfr(12, 400))
print("Zero cases (0/0):  ", compute_cfr(0, 0))

Expected Output:

Valid CFR (12/400): 3.0
Zero cases (0/0):   None

10.3.4 Custom Domain Exception (InvalidVitalSignError)

When your research package grows past a handful of functions, subclassing ValueError lets you create a self-documenting clinical exception in just two lines:

class InvalidVitalSignError(ValueError):
    """Raised when a clinical vital sign is outside human bounds."""

def check_temp(temp_c):
    """Validate human body temperature in [30.0, 45.0] C."""
    if isinstance(temp_c, bool) or not isinstance(temp_c, (int, float)):
        raise InvalidVitalSignError(f"Non-numeric temp: {temp_c!r}")
    if not (30.0 <= temp_c <= 45.0):
        raise InvalidVitalSignError(f"Implausible temp: {temp_c} C")
    return float(temp_c)

for sample in [37.4, 41.2, 999.0]:
    try:
        clean = check_temp(sample)
        print("Accepted:", clean)
    except InvalidVitalSignError as exc:
        print("Flagged vital sign:", exc)

Expected Output:

Accepted: 37.4
Accepted: 41.2
Flagged vital sign: Implausible temp: 999.0 C

Because InvalidVitalSignError inherits from ValueError, callers can catch it specifically with except InvalidVitalSignError: or generically with except ValueError:. Also notice the isinstance(temp_c, bool) guard—in Python, bool is a subclass of int (isinstance(True, int) is True!), so checking bool explicitly is an essential defensive habit.

10.3.5 Automated Unit Testing: assert & pytest-Style Test Functions

Python’s built-in assert condition, "optional message" statement does nothing when condition is True and raises AssertionError immediately when condition is False. Grouping assertions into small test_*() functions follows the exact convention used by pytest—Python’s industry-standard testing framework:

def test_compute_cfr_nominal():
    assert compute_cfr(12, 400) == 3.0
    assert compute_cfr(0, 250) == 0.0

def test_compute_cfr_zero_cases():
    assert compute_cfr(0, 0) is None

def test_compute_cfr_rejects_negatives():
    try:
        compute_cfr(-3, 100)
    except ValueError:
        pass
    else:
        raise AssertionError("Expected ValueError for negative deaths")

for test_fn in (
    test_compute_cfr_nominal,
    test_compute_cfr_zero_cases,
    test_compute_cfr_rejects_negatives,
):
    test_fn()
    print(f"PASS: {test_fn.__name__}")

Expected Output:

PASS: test_compute_cfr_nominal
PASS: test_compute_cfr_zero_cases
PASS: test_compute_cfr_rejects_negatives

Look closely at test_compute_cfr_rejects_negatives: a good test suite verifies not only that valid inputs return the right numbers, but also that invalid inputs actually raise the promised exception! In a standalone .py project tested with pytest, you can write that same check concisely using with pytest.raises(ValueError): compute_cfr(-3, 100).

10.3.6 Break It On Purpose! (Exception & Testing Error Anatomy)

ImportantBreak It On Purpose #1 — ValueError From Explicit Defensive Raise 
bad_cfr = compute_cfr(-5, 100)

Python’s Traceback:

ValueError: deaths and cases must be non-negative

Diagnosis: Our explicit guard clause inside compute_cfr intercepted a physically impossible negative death count (-5) and stopped execution immediately with a human-readable message rather than returning a nonsensical -5.0% fatality rate.
Fix: Catch ValueError in the calling batch pipeline (quarantining the row) or correct the upstream data entry before calling compute_cfr.

ImportantBreak It On Purpose #2 — AssertionError Catching a Broken Epidemiological Formula 
def buggy_cfr(deaths, cases):
    return round(deaths / cases, 2)   # Forgot * 100!

assert buggy_cfr(12, 400) == 3.0, "Expected 3.0%, got wrong scale!"

Python’s Traceback:

AssertionError: Expected 3.0%, got wrong scale!

Diagnosis: buggy_cfr(12, 400) returned 0.03 (a proportion) instead of 3.0 (a percentage). Without an automated assert, this \(100\times\) scale error could silently flow straight into a manuscript table!
Fix: Multiply by 100 (round((deaths / cases) * 100, 2)) and re-run the test suite to confirm PASS.

ImportantBreak It On Purpose #3 — Uncaught KeyError on Missing Nested Dictionary Key 
report = {"Dhaka": {"cases": 140}}
dhaka_icu = report["Dhaka"]["icu_beds"]

Python’s Traceback:

KeyError: 'icu_beds'

Diagnosis: "Dhaka" existed in report, so the first lookup succeeded, but the inner dictionary did not contain "icu_beds". Direct bracket indexing without exception handling crashed the entire script.
Fix: Wrap nested lookups in an EAFP helper (get_metric(report, "Dhaka", "icu_beds")) catching (KeyError, TypeError) and returning None.

10.4 Stage 4 — The Researcher’s Problem-Structuring Blueprint

Scenario: A maternal health mobile survey uploads daily batches of raw intake dictionaries (patient_id, temp_c, sbp_mmhg). Some rows arrive as numeric strings ("37.8"), some contain impossible sentinel temperatures ("999"), and some drop required keys entirely. Build a two-layer defensive pipeline—a strict single-row validator raising InvalidVitalSignError and a resilient batch processor that quarantines corrupt rows without crashing—and verify it with assert.

10.4.1 Blueprint (Completed on Paper Before Coding)

  1. Layered Architecture (Single Responsibility):
    • validate_intake_row(row) \(\rightarrow\) enforces required keys (patient_id, temp_c, sbp_mmhg), numeric casting, and physiological bounds (\(30.0 \le \text{temp\_c} \le 45.0\), \(50.0 \le \text{sbp\_mmhg} \le 260.0\)); raises InvalidVitalSignError on any violation.
    • process_intake_batch(raw_rows) \(\rightarrow\) loops with enumerate(raw_rows), catches InvalidVitalSignError per row into quarantine, appends clean dicts in else: to accepted, and returns (accepted, quarantine).
  2. Edge Cases & Traps:
    • Calling float(row["temp_c"]) before verifying "temp_c" in row leaks KeyError instead of InvalidVitalSignError.
    • Catching InvalidVitalSignError inside the loop (not outside!) ensures row 1’s failure never aborts rows 2 and 3.
  3. Verification Plan (Hand Check):
    • Input batch has 4 rows: M-01 (valid string numbers), M-02 (temp_c="999" \(\rightarrow\) quarantined), M-03 (missing sbp_mmhg \(\rightarrow\) quarantined), M-04 (valid numeric values).
    • Expected result: len(good) == 2 and len(bad) == 2.

10.4.2 Clean Python Implementation (Verbatim in 01_walkthrough.ipynb)

def validate_intake_row(row):
    """Validate one clinic intake dict or raise InvalidVitalSignError."""
    for key in ("patient_id", "temp_c", "sbp_mmhg"):
        if key not in row:
            raise InvalidVitalSignError(f"Missing field: {key}")
    try:
        temp_c = float(row["temp_c"])
        sbp = float(row["sbp_mmhg"])
    except (ValueError, TypeError) as exc:
        raise InvalidVitalSignError(f"Non-numeric vital: {exc}")
    if not (30.0 <= temp_c <= 45.0):
        raise InvalidVitalSignError(f"Bad temp_c: {temp_c}")
    if not (50.0 <= sbp <= 260.0):
        raise InvalidVitalSignError(f"Bad sbp_mmhg: {sbp}")
    return {"patient_id": row["patient_id"], "temp_c": temp_c, "sbp": sbp}

def process_intake_batch(raw_rows):
    """Return (accepted_rows, quarantine_log) without crashing."""
    accepted = []
    quarantine = []
    for idx, row in enumerate(raw_rows):
        try:
            clean = validate_intake_row(row)
        except InvalidVitalSignError as exc:
            quarantine.append(f"Row {idx}: {exc}")
        else:
            accepted.append(clean)
    return (accepted, quarantine)

sample_rows = [
    {"patient_id": "M-01", "temp_c": "37.8", "sbp_mmhg": "118"},
    {"patient_id": "M-02", "temp_c": "999", "sbp_mmhg": "120"},
    {"patient_id": "M-03", "temp_c": "38.6"},
    {"patient_id": "M-04", "temp_c": 36.7, "sbp_mmhg": 142},
]
good, bad = process_intake_batch(sample_rows)
assert len(good) == 2 and len(bad) == 2
print("Accepted:", good)
print("Quarantined:", bad)

Output:

Accepted: [{'patient_id': 'M-01', 'temp_c': 37.8, 'sbp': 118.0},
           {'patient_id': 'M-04', 'temp_c': 36.7, 'sbp': 142.0}]
Quarantined: ['Row 1: Bad temp_c: 999.0', 'Row 2: Missing field: sbp_mmhg']

10.8.1 A. Concept & Execution Trace Test Key

  1. Prints B then C (try succeeded, so except is skipped, else runs, and finally always runs).
  2. Prints A then C (ValueError jumps to except, else is skipped, and finally always runs).
  3. A bare except: silently swallows real programming bugs (NameError, Syntax-like runtime typos, ZeroDivisionError) and even KeyboardInterrupt, masking root causes during debugging.
  4. Zero cases (0, 0) is a legitimate surveillance week with an undefined ratio (None), whereas negative deaths (-2) is physically impossible corrupt data that must fail loudly with ValueError.
  5. isinstance(True, int) evaluates to True because bool subclasses int (True == 1, False == 0). Without isinstance(val, bool), boolean flags could silently masquerade as patient counts!
  6. TypeError ('<' not supported between instances of 'str' and 'float'). Always validate types before numeric range comparisons.
  7. except ValueError: catches InvalidVitalSignError (Yes—subclasses match parent handlers). The reverse is No: except InvalidVitalSignError: will not catch a plain ValueError.
  8. If try / except wraps the outside of the loop, the very first bad row exits the entire loop immediately, abandoning every valid record that follows it!
  9. A constant dummy function lambda w, h: 20.0 passes any single test expecting 20.0. Testing at least two inputs with different expected BMIs (e.g., 20.0 and 25.0) exposes hardcoded shortcuts immediately.
  10. Read from the bottom up: the final line names the exact exception type and message, and the innermost frame immediately above points to the exact expression that triggered the failure.

# Exam Task 10.1 (30 pts)
def parse_patient_record(raw_dict):
    """Validate patient record dict and return clean typed dict."""
    if not isinstance(raw_dict, dict):
        raise ValueError("Record must be a dictionary")
    for key in ("patient_id", "temp_c", "hb_g_dl"):
        if key not in raw_dict:
            raise ValueError(f"Missing required key: {key}")
    raw_pid = raw_dict["patient_id"]
    if not isinstance(raw_pid, str) or not raw_pid.strip():
        raise ValueError("patient_id must be a non-empty string")
    pid = raw_pid.strip()
    raw_temp = raw_dict["temp_c"]
    raw_hb = raw_dict["hb_g_dl"]
    if isinstance(raw_temp, bool) or isinstance(raw_hb, bool):
        raise ValueError("Clinical vitals cannot be boolean")
    try:
        temp_c = float(raw_temp)
        hb_g_dl = float(raw_hb)
    except (ValueError, TypeError) as exc:
        raise ValueError(f"Non-numeric vital sign: {exc}")
    if not (30.0 <= temp_c <= 45.0):
        raise ValueError(f"temp_c out of range [30.0, 45.0]: {temp_c}")
    if not (2.0 <= hb_g_dl <= 25.0):
        raise ValueError(f"hb_g_dl out of range [2.0, 25.0]: {hb_g_dl}")
    return {"patient_id": pid, "temp_c": temp_c, "hb_g_dl": hb_g_dl}

# Exam Task 10.2 (35 pts)
def batch_validate_records(raw_records):
    """Validate records via parse_patient_record without crashing."""
    valid_list = []
    rejected_errors = []
    for record in raw_records:
        try:
            cleaned = parse_patient_record(record)
        except ValueError as exc:
            rejected_errors.append(str(exc))
        else:
            valid_list.append(cleaned)
    return (valid_list, rejected_errors)

# Exam Task 10.3 (35 pts)
def compute_safe_odds_ratio(a, b, c, d):
    """Validate non-negative ints (not bool); return OR or None."""
    for val in (a, b, c, d):
        if isinstance(val, bool) or not isinstance(val, int) or val < 0:
            raise ValueError(f"Invalid 2x2 cell count: {val!r}")
    if b == 0 or c == 0:
        return None
    return round((a * d) / (b * c), 2)

10.8.4 D. Debugging Post-Mortem: Top 3 Chapter 10 Failure Modes

  1. Leaking KeyError or TypeError When ValueError Was Promised: In Tasks 10.1 and 10.3, comparing "37.5" < 30.0 or indexing raw_dict["hb_g_dl"] before checking types and keys raises TypeError or KeyError, slipping past a batch handler that listens only for except ValueError:. Always validate structure and types first so every contract violation surfaces consistently as ValueError.
  2. Forgetting That bool Is a Subclass of int: Calling isinstance(True, int) returns True in Python. In clinical counts (compute_safe_odds_ratio) and vital-sign validators (validate_body_temp), always reject isinstance(val, bool) explicitly before checking isinstance(val, int).
  3. Wrapping the Outer Loop Instead of Each Record: Placing try / except ValueError: outside for record in raw_records: aborts the entire cohort the instant one bad tablet entry appears. Always keep try / except tightly scoped to the single operation that can fail, and verify your recovery logic with automated assert tests!
